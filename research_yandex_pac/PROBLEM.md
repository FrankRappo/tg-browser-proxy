# ПРОБЛЕМА: Яндекс.Браузер игнорирует PAC-прокси на дефолтном профиле

## Задача для реверс-инженера

Найти в коде/конфигурации Яндекс.Браузера механизм, который **отменяет результаты
PAC-резолвинга прокси на дефолтном профиле**, и найти управляемый извне способ
его отключить/обойти (скрытая политика, флаг, ключ Local State, API, файл).

Если способ найдётся — Telegram-through-tunnel можно будет включить в Яндексе
«как у Chrome» (любой запуск), без отдельного профиля и ярлыка (текущий workaround:
`../yandex_broweser/README.md`).

## Окружение

| Параметр | Значение |
|---|---|
| ОС | Windows 10 Pro 19045.6456 x64 |
| Яндекс.Браузер | 26.10.0.0, движок Chromium **152.0.7977.1818** (User-Agent: `...Chrome/152.0.0.0 YaBrowser/26.10.0.0`) |
| Профиль | дефолтный (`User Data\Default`), пользователь залогинен в Яндекс-аккаунт (sync вкл.) |
| Бинарники | `C:\Program Files\Yandex\YandexBrowser\Application\` (browser.exe + dll) |

## Симптом (кратко)

1. Запуск `browser.exe --proxy-pac-url=http://127.0.0.1:8081/proxy.pac` на дефолтном профиле:
   - PAC **скачивается** (нетлог: TCP connect к 127.0.0.1:8081 OK, HTTP/1.1 200 OK,
   Content-Length: 388, `Content-Type: application/x-ns-proxy-autoconfig`);
   - НО все URL-резолвы возвращают `[direct://]` — включая тестовый PAC, который
   для ЛЮБОГО хоста (кроме localhost) возвращает `SOCKS5 127.0.0.1:1080`.
   Т.е. движок PAC либо не исполняется, либо его результат отбрасывается и
   подменяется на DIRECT.
2. На **свежем профиле** (`--user-data-dir=<новая папка>`) тот же флаг **работает**:
   PAC исполняется, трафик идёт в SOCKS. Разница — только в состоянии профиля.
3. В `Default\Secure Preferences` на дефолтном профиле найден вшитый узел:
   ```json
   "proxy": {
     "mode": "pac_script",
     "pac_mandatory": false,
     "pac_url": "data:application/x-ns-proxy-autoconfig;base64,Y29uc3QgY291bnRyaWVzP..."
   }
   ```
   Base64-префикс декодируется как `const countriesP...` — похоже на их внутренний
   скрипт country-routing (обход блокировок / антишок / выдача по странам).
   **Этот узел — главный подозреваемый.**
4. Удаление/подмена этого узла в файле переживает запуск (файл пересобирается),
   но PAC всё равно не применяется; при некоторых сценариях узел возвращается
   (подозрение на восстановление из облачной синхронизации или сервисом самого браузера).
