# Chrome: почему первая проверка не прошла

Дата: 2026-11-09. Проверялась удалённая машина `DESKTOP-RL10OMC` после настройки
Telegram-only прокси. Итоговая настройка Chrome была правильной, но первая автоматическая
проверка дала ложно-негативный результат.

## Что было уже настроено правильно

- BAT-канал поддержки был активен: relay-порты профиля `2353/2354` слушали.
- PAC-сервер отвечал `200`, туннель отвечал через SOCKS5 (`socksTelegramExit=0`).
- В HKLM уже были политики Chrome:
  - `ProxyMode=pac_script`
  - `ProxyPacUrl=http://127.0.0.1:8081/proxy.pac`
- Ярлыки Яндекса использовали `C:\BT-Proxy\ya_tg` и тот же PAC URL.

## Почему первая проверка выглядела неуспешной

1. Исторический проверочный скрипт, сохранённый только локально, проверял PAC так:
   `([string]$r.Content).Contains('SOCKS5 127.0.0.1:1080')`. Для ответа
   `Invoke-WebRequest` содержимое PAC могло прийти как `byte[]`; преобразование в
   `[string]` давало `System.Byte[]`, поэтому проверка возвращала `False`, хотя файл был
   корректным. Правильная проверка — декодировать `byte[]` в UTF-8, как в
   `remote_proxy_verify.ps1`, после чего `pacHasSocksRule=true`.
2. Headless Chrome `--dump-dom` через PowerShell возвращал `domLen=0` без stderr и без
   созданного PNG. Это не доказывало ошибку PAC: на Chrome 157 и удалённом PowerShell
   stdout/headless-артефакты оказались ненадёжным способом приёмки. Первый probe `.cmd`
   отдельно дал `9009`, потому что путь `C:\Program Files\Google\Chrome\...` был без
   кавычек; после исправления захват stdout всё равно оставался пустым.
3. Ошибка `REMOTE HOST IDENTIFICATION HAS CHANGED` в начале сессии означала, что под тем же
   портом профиля появился другой ПК, а не что Chrome настроен неверно. После обновления
   `windows_known_hosts` вход на актуальную машину прошёл.

## Как проверять Chrome после этого

Не считать пустой `--dump-dom` признаком отказа прокси. Использовать два независимых
факта:

1. Реестр и PAC: `remote_proxy_verify.ps1`.
2. CDP на отдельном профиле: `scripts/remote_chrome_cdp_verify.ps1`.

Ожидаемый доказательный результат CDP:

```text
cdpVersionEndpoint=true
cdpTargetUrl=https://web.telegram.org/k/
cdpTargetTitle=Telegram Web
cdpTelegramObserved=true
```

Отдельный `--user-data-dir` обязателен: в Chrome 136+ CDP-порт на дефолтном профиле
блокируется. После диагностики временные профили, netlog и файлы проверки удаляются.
